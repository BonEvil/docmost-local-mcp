The resulting exact contracts are:

- `delete_page`: `POST /api/pages/delete` with canonical `pageId` and
  `permanentlyDelete: false`. Docmost recursively marks the active target and
  descendants deleted and removes their active shares. This is trash, not a
  permanent purge.
- `delete_space`: `POST /api/spaces/delete` with canonical `spaceId`. Docmost
  permanently deletes the space, database constraints cascade space-owned
  records, and the service queues attachment cleanup.
- `delete_comment`: `POST /api/comments/delete` with canonical `commentId`.
  The comment row is permanently deleted and its parent-comment foreign key
  cascade-deletes threaded replies.

## Exact allowlist, metadata, and result contract

`WRITE_TOOL_NAMES` is locked by test to these thirteen names:

```text
create_page, update_page, duplicate_page, copy_page_to_space, move_page,
move_page_to_space, create_space, update_space, create_comment, update_comment,
delete_page, delete_space, delete_comment
```

The default server still exposes exactly ten read-only tools. Write mode with a
nonempty exact allowlist exposes only the named subset; read-only plus any write
name, empty write mode, unknown names, duplicates, and empty entries fail at
startup. Each delete is exposed only when its exact name is configured.

All deletes require a canonical UUID. Each declares `readOnlyHint: false`,
`destructiveHint: true`, and `idempotentHint: false`. Tool descriptions and
input-schema descriptions state the stable target and cascade/permanence
consequence. Successful calls populate MCP `structured_content` with `outcome`,
`target`, `consequence`, and `automaticRetry: false`; only the validated UUID
and code-owned labels appear.

## Failure safety

Delete requests deliberately disable the ordinary single-401 replay. Each tool
call can dispatch at most one destructive HTTP request. Any unconfirmed result
requires an independent target read before another confirmation.

`tests/docmost_delete_test.rs` passed eight focused tests covering:

- exact endpoint/payload contracts for all three deletes;
- malformed stable identifiers rejected before dispatch;
- unknown/already absent `404`, `401`, `403`, `409`, and `500` failures with no
  automatic retry and no committed mock deletion;
- one explicit successful deletion followed by an already-absent duplicate,
  proving two calls produce one deletion;
- redirect refusal with zero target hits;
- timeout after an ambiguous server-side commit with exactly one dispatch;
- oversized success response failure after exactly one dispatch; and
- caller interruption with exactly one started request and no replay.

The inherited network suite separately passed fixed connect/request timeouts,
streaming input/output caps, safe response omission, and no-redirect behavior.

## Residual risk

- A timeout or interruption can leave a delete committed with no success
  response. The client does not claim success and never retries; an operator
  must independently inspect the target and obtain a new confirmation.
- Docmost performs space attachment cleanup asynchronously after the database
  deletion. The live fixture contained no attachment bytes; the queue contract
  is pinned to v0.95.0 primary source and the successful space response, but
  queue-worker deletion of an actual object was not exercised by this card.
- `delete_page` intentionally implements the reversible v0.95.0 trash path. It
  does not expose permanent page purge.
